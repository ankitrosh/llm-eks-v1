# V3.4 Generalized Framework — Freeze Report

Date: November 13, 2026 (Pacific Time)

## Decision

V3.4 feature development is frozen.

The supported extension contracts, external backend integration,
model inspection customization, Kubernetes deployment customization,
and real vLLM scheduler replacement have been implemented and validated.

This is a validated research/framework milestone, not a claim of
production readiness or compatibility with arbitrary vLLM internals.

## Architecture

The framework uses three complementary design patterns:

1. Strategy: selectable runtime behaviors and implementations.
2. Registry/Factory: explicit plugin registration, capability
   validation, and construction.
3. Adapter: stable framework-facing interfaces around externally
   supplied backends and execution components.

The implementation uses explicit selection and fails closed for
unsupported or incompatible extensions.

## Implemented Capabilities

### Model inspection

- Architecture-dispatched model inspector registry.
- Built-in Qwen3 checkpoint and layout inspection.
- External InspectorSpec registration.
- Public CLI --inspector-module support.
- Artifact provenance and layout consistency checks.
- Rejection of unsupported architectures and invalid artifacts.

### External execution backends

- User-defined backend registration through PluginRegistry.
- ExternalBackendAdapter lifecycle and response validation.
- Backend validation, preparation, startup, generation, cancellation
  interface, health checking, and shutdown.
- Minimal HTTP integration for non-streaming completions.
- Unsupported streaming requests explicitly rejected.

### Scheduling

- User-defined scheduling policies via external modules.
- Validated translation into vLLM launch parameters.
- Runtime class replacement through --scheduler-cls.
- Python scheduler mounted through Kubernetes ConfigMap without
  modifying the framework or rebuilding the pinned vLLM image.

### Kubernetes resources

- CPU request and limit overrides.
- Memory request and limit overrides.
- Validated GPU resource requests and limits.
- GPU topology changes rejected when incompatible with the
  existing execution plan.
- Overrides rendered consistently for both distributed workers.
- Default manifests preserved when no override is supplied.

### Research-runtime extensions

- Model adapters and per-layer attention extension interfaces.
- Plugin contract checking and explicit compatibility handling.
- Research-runtime components remain distinct from native
  vLLM implementation hooks.

## Known Limitations

1. Arbitrary native vLLM KV-cache implementation replacement
   is not integrated or GPU validated.

2. Research-runtime custom attention support does not imply
   arbitrary native vLLM attention-kernel replacement.

3. The tested custom scheduler is intentionally minimal:
   it proves runtime replacement rather than an alternative
   scheduling algorithm.

4. Custom vLLM scheduler classes depend on upstream internal
   APIs and require compatibility checks when upgrading vLLM.

5. The external backend demo is a CPU-only test implementation,
   not a validated user-provided distributed LLM engine.

6. The external inspector example demonstrates registration
   and dispatch but does not verify real custom-model checkpoint
   weights.

7. CPU and memory overrides are validated syntactically and
   for request/limit consistency; they do not guarantee that
   the selected node hardware has sufficient resources.

8. Production-scale durability, security hardening, sustained
   load, and arbitrary-model compatibility are not certified.

## V3.5 Scope

V3.5 is dedicated to repository and release preparation:

- Separate stable framework code from archived research.
- Organize source, tests, deployment manifests, and examples.
- Add README, LICENSE, setup instructions, and CI.
- Document three user workflows:
  1. Use the default framework.
  2. Swap supported models/configuration.
  3. Supply custom extensions or execution backends.
- Add reproducible verification and deployment instructions.
- Prepare the public release.

No new inference optimization or distributed scheduling feature
is required for the V3.4 freeze.
